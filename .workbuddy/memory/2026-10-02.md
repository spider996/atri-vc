### 用户反馈

（注：用户原话有重复，语义是「那就用 root 吧，但没 root 的人怎么办」）

### 1. 设备 root 状况（实测）

- `ro.boot.verifiedbootstate=green` / `ro.boot.flash.locked=1` / **未解锁 BL**
- 无 `su`、无 `/data/adb/magisk`
- 机型代号 **`dali`**，HyperOS **OS3.0.301.0.WONCNXM**（国行），Android 16
- `crypto.type=file`（FBE）

### 2. 国行 HyperOS 3 解锁门槛（查证）

需**同时**满足：社区成长等级 5 段 + 通过答题测试 + 实名认证 +
同账号全流程绑定（有效期 336 小时）+ 每年最多 3 台；
**解锁会清空全部数据**，且**解锁后收不到 OTA 更新**。
→ 用户决策：**放弃 root**。

### 3. ⚠️ 耳机声学回环被实测证伪（重要）

写了 `HeadsetLoopTest.kt` + `LOOPTEST` 调试通路做判别实验。

**第一轮结果（A2DP 默认通路）：**

| 项目 | 值 |
|---|---|
| 静音基线 | **-112.7 dBFS** |
| 播放+录音 | **-114.5 dBFS** |
| 回环增益 | **-1.8 dB** |
| 实际输出设备 | iKF-King Pro⁺ ✅ |
| 实际输入设备 | iKF-King Pro⁺ ✅ |

**设备层面全对，声音完全传不过去。**

### 根因：A2DP 与 HFP/SCO 是两条独立链路

- `A2dpStateMachine state=Connected` —— 放音走高音质 A2DP，**不走 SCO**
- `HeadsetStateMachine state=Connected` —— 麦克风在 HFP 这条路上
- **耳机硬件不会把「喇叭收到的」和「麦克风发出的」内部接通**；
  两者在蓝牙协议层就是分离的。
- 唯一物理声学路径是「耳机喇叭 → 空气 → 耳机麦」，
  但入耳式耳机喇叭冲耳道、麦克风朝外，被耳壳隔开，声压极低。
- 旁证：`录音source=7`（VOICE_RECOGNITION），说明 `VOICE_COMMUNICATION(3)`
  都没拿到 → SCO 输入未真正激活。

→ **注意：这条结论推翻了我上一轮的「方案已真机验证通过」。**
  上一轮只验证了「输出确实到了耳机」，**没验证「耳机麦能收到耳机喇叭的声音」**——
  这是两件不同的事。教训：验证要验到「最终目的事实」，不能验到中间环节就宣布成功。

### 4. 最后一搏：主动建立 SCO 的对照实验

给 `HeadsetLoopTest` 加了第 2 组实验：
`startBluetoothSco()` + `API31+ setCommunicationDevice(btDevice)`，
然后重测回环增益。若 SCO 组有效 → 方案有救；否则彻底作废。

### 5. Shizuku 路线探明（用户放弃 root 后的备选）

- Shizuku 提供 **shell (adb) 权限**，不 root、不解锁、不清数据
- 但实测 `cmd audio` **没有任何 SCO/蓝牙路由子命令**（只有音量、环绕格式）
- `cmd bluetooth_manager` 也只有 enable/disable/wait-for-state
- → **shell 权限下没有现成的音频路由开关**，Shizuku 未必能强制 SCO

### 6. 保留的工具（有复用价值）

`HeadsetLoopTest.kt` + `LOOPTEST` 触发文件 =
**判别任何「声学回环」方案成立与否的标准工具**。
测「静音基线」vs「播放时能量」，差值 < 3 dB 就是没回环。
比「用耳朵听 QQ 里有没有声音」快得多、可靠得多。

## ⭐ 后续：找到可行通路 —— 扬声器外放（同日晚）

### 用户的关键反驳

> **先别急着否定，我手机里有一个橘雪梨变声器，人家就可以使用qq录音啊**

这条推翻了「非 root 不可能」的过悲观结论，是本轮最重要的转折。

### 查证到的真相

搜到同类产品**橘雪莉语音盒**的官方教程，原文：

> 想在 QQ 里顺利开启变音整活吗？……**必须依托系统自带的小窗口或者应用双开小屏功能**
> 才可以完美激活；要是直接切进大型网络游戏里往往是不管用的，主要是因为游戏官方
> 从底层做了权限屏蔽，导致麦克风对面的队友根本听不到声音。
>
> 依旧是以主流的小米机型作为操作示范，该玩法**仅在系统支持分屏或悬浮小屏的模式下**
> 才能派上用场。

**关键洞察**：免 root 变声器能用的原因**不是「注入音频」**（那确实没有 API），
而是 **「扬声器外放 → 手机自带麦」+「用系统小窗/分屏让 QQ 保持前台」**。
用返回键切到变声器 → QQ 退后台 → 采集被暂停 → 「录音里没有任何声音」。
**这才是最初问题的真正原因**，与我们之前一直排查的耳机回环无关。

### 真机取证：非 root 铁律

```
adb shell dumpsys media.audio_policy | grep AUDIO_DEVICE_IN
```

Available input devices **只有 5 个**，全是物理设备或系统内部通路：

```
"Built-In Mic"        AUDIO_DEVICE_IN_BUILTIN_MIC
"BT SCO Headset Mic"  AUDIO_DEVICE_IN_BLUETOOTH_SCO_HEADSET
"Voice Call In"       AUDIO_DEVICE_IN_TELEPHONY_RX
"Built-In Back Mic"   AUDIO_DEVICE_IN_BACK_MIC
"Remote Submix In"    AUDIO_DEVICE_IN_REMOTE_SUBMIX
```

**没有任何虚拟麦克风设备** → 证实「第三方 App 无法新增输入设备 / 无法注入别人的麦克风」。

## ⭐⭐ 用户第二次反驳：「橘雪梨在小窗模式下不用外放就能变声」

### 做法：直接把 APK 拉下来拆（不要靠搜网页/猜）

搜网页只有 PC 端虚拟声卡方案，没有 Android 免 root 的实证。
于是**从用户手机上拉取该 App 的 APK 逆向**：

```bash
adb shell pm path com.bluegogo.bluegogo.qw.jxl     # 先定位包名
adb pull /data/app/.../base.apk                    # 拉下来
```
包名 `com.bluegogo.bluegogo.qw.jxl` v1.04，30.11 MB（**`jxl` = 橘雪梨首字母**，
是 `pm list packages -3` 里靠关键字猜出来的）。

### 结论：它根本不具备变声能力（7 条铁证）

| 检查项 | 结果 |
|---|---|
| `RECORD_AUDIO` 权限 | **✗ 没有** → 连读麦克风都做不到 |
| `MODIFY_AUDIO_SETTINGS` | **✗ 没有** |
| `CAPTURE_AUDIO_OUTPUT` | **✗ 没有** |
| 原生 SO | 全是广告 SDK（pangle/穿山甲、octopus、sgcore、windmill、kwad、sigmob）|
| 变声 DSP/NN 库 | **一个都没有**（无 SoundTouch/rubberband/WSOLA/TFLite）|
| APK 内置音频文件 | **0 个**（按魔数扫描；那些 .webp 被 `RIFF` 误判不算）|
| 运行时录音客户端 | `dumpsys media.audio_flinger` → **`- No active record clients`** |
| 主界面 | `com.webviewapp.pro.main` → **WebView 壳** |

**它实际做的**：从服务端拉**预录语音包**，点击后**从扬声器大声播出**。
「原声/胖猫/花栗鼠」是素材分类标签，不是实时变声。
「小窗」只是让你能一边看 QQ 一边点播放。

→ **「不用外放」这个前提在证据层面不成立**；声音必然经空气（或耳机）回采。
→ 待用户确认：用它时手机扬声器是否在响。

### 可复用的方法论（重要）

**当某个 App 宣称能做到我们做不到的事时，不要靠搜索或推理，
直接把它的 APK 拉下来查权限清单和 SO 库。** 这比任何二手资料都硬。

关键命令：
```bash
adb shell dumpsys package <pkg> | sed -n '/requested permissions:/,/install permissions:/p'
adb shell dumpsys media.audio_flinger | grep -E 'record clients|Active'
```
- **权限清单是最快的判据**：没有 `RECORD_AUDIO` 就绝无可能读麦克风
- **SO 库名单能看出它用的是什么技术栈**：全是广告 SDK 就说明是个壳
- **`No active record clients` 能证明它运行时根本没在录音**

Python 侧用 `zipfile` 读 APK，按魔数（而非扩展名）扫音频，
并解析 DEX 字符串表看包名分布（判断哪些代码属于 App 自身、哪些是 SDK）。
脚本：`tools/scan_jxl_dex.py`、`tools/jxl_strs.py`、`tools/jxl_audio.py`。

## 第三次反馈：学橘雪梨的**交互形态**（悬浮小窗 + 不循环 + 音量温和）

> 用户原话：「那就只能使用外放了，但是橘雪梨那个有参考价值，可以参考他的小窗流程来外放转换或合成好的音频，
> 这比直接切换界面方便很多，也不需要循环播放，另外，外放时别把音量一下子挑满，很容易吓人一跳啊」

**方向**：学交互，不学原理。橘雪梨的原理已证伪（无 RECORD_AUDIO / WebView 壳），
但它「悬浮球浮在 QQ 上点一下就播」的形态是对的。

### 做了什么

1. **新增 `FloatingPlayService`**（`SYSTEM_ALERT_WINDOW` 前台服务）
   - 悬浮球 58dp，可拖动（位置落盘），点击 = 播放 / 停止
   - `TYPE_APPLICATION_OVERLAY` + **`FLAG_NOT_FOCUSABLE`**（不加会抢焦点，QQ 的「按住说话」直接失效）
   - Android 14 起 `startForeground` 必须传 `FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK`
   - 拖动 + 点击二合一：不能同时用 `setOnClickListener`（onTouch 消费后它不再触发），
     自己在 `ACTION_UP` 里判「位移 < 8dp 且按下 < 400ms」
2. **去掉循环**：主入口改 `playNow`（点一次播一遍）；`QQ_LOOP_SEC` 只留给无障碍自动触发
3. **音量温和化**（用户说「吓人一跳」）
   - 只抬到 max 的 **70%**，且只在「当前更小」时才抬
   - `setVolume` 做 350ms 淡入（25ms 一步，14 步），`start()` 前先归零
   - **三个恢复点**：`onCompletion` / `stopInternal` / `catch` 都要恢复原音量

### 实测端到端验证（重点）

```
点悬浮球 → VoiceSender[外放] 音量 4 -> 21 / 30（70%，播完恢复）
        → route=SPEAKER usage=1 耳机=无！ 输入=手机麦
        → 实际输出设备已解析：25060RK16C（扬声器）
        → 3.46 秒后「播放结束」→ 音量已恢复为 4
```

**三条要求全部拿到日志证据。**

### 顺手修掉的两个真实 Bug

1. **交互层级错**：整张 QQ 卡片包在 `if (qqAutoSend)` 里，而它默认 false →
   **悬浮窗入口不可达**。改成常显，无障碍开关降级为卡片末尾的可选项。
2. **老用户迁移缺失**：`qqHeadsetMode=true` 是已证伪时代的默认值，
   `getBoolean(key, false)` 遇已存在的 key 会读旧值 → **升级后仍停在耳机模式**，
   表现为「点了播但 QQ 里没声音」。加 `routeMigrated` 版本键做一次性迁移。

### 新发现的坑（已写进技能 android-audio-loopback-verify）

- **蓝牙没断时「外放」是假外放**：`STREAM_MUSIC` 被路由到 `bt_a2dp`，声音进耳机不进空气。
  实测中确实撞到了（`Devices: bt_a2dp(80)`）。已加 `lastBlockedByHeadset` 状态 + 设置页红色警告卡片。
- **`dumpsys window` 定位悬浮窗要用 `frame=`，不能用 `mAttrs`**：
  `mAttrs` 的 y 没算系统栏偏移，实测差了 152px（正好状态栏高），直接拿去 `input tap` 会落空。
- **`appops set SYSTEM_ALERT_WINDOW allow` 不等于 `canDrawOverlays()` 为 true**：
  实测 appops 显示 allow，App 内仍返回 false，必须真的走系统授权页点一下。
- **`input tap` 在这台 ROM 上对新启动的进程不稳定**（同样坐标有时中有时不中）；
  但悬浮球窗口和系统设置页是能点中的。自动化验证优先走「不依赖 `input`」的路径。

### ④ 合成偶发失败 → 真因 = **EOS 门控 off-by-one**（本轮最重要的修复）

**真机 logcat 崩溃堆栈**（合成「我只有两岁！」高兴情绪，3 次全失败）：

```
onnxruntime: Non-zero status code returned while running Gather node.
   ... idx=1024 must be within [-1024,1023]      (TtsEngine.kt:493，调 vits 处)
```

**根因**：AR 循环里「前 minSteps 步**禁用** EOS」的条件**写反**了 ——
旧 Kotlin `useEos = idx <= minSteps` 使**前 45 步反而允许 EOS**，
且 `break` 被 `!useEos` 的门槛挡掉 → **EOS(1024) 被写进 `sem`** → 喂给 vits → `codes` 查表越界。
（⚠️ vits 的 `codes` 词表只有 **0..1023**，**1024 是 EOS 哨兵**，绝不能进 vits。）

**PC 对照**：`tools/gsv_onnx_pipeline.py:235`
`lg_use = lg[:, :-1] if idx <= min_steps else lg`（前 minSteps 步**屏蔽掉 EOS 那一列**）。

**修法**（`tools/patch_tts_eos.py`）：

1. `prepareLogits()` 单独拆出：含重复惩罚 + **正确屏蔽 EOS**，返回 logits **副本**；
2. `sample(logits, topK, topP, temp, rng)` 去掉 `useEos` 参数；
   **无条件判停** `if (argmaxEos || sampled >= EOS) break`；
3. **永不把 EOS 写进 y/sem**；AR 收尾加 **400 帧截断兜底** + 双保险把 `>= EOS` 的 token 替换为 0。

**验证**：复现用例 → `AR 步数=48 EOS停止=true`，vits 正常输出 **1.92s wav**，再无 Gather 越界。

### ⚠️ 踩坑：`build-real.ps1` 的 adb 抢跑

构建脚本里 `adb install` 是**第一条 adb 命令**，若 adb 守护进程当时没在跑，
它自己会去启动守护进程，**但本次调用已经返回 `device '<serial>' not found`** → 安装失败（构建本身是成功的）。
此时 `adb devices` 已能看到设备，**手动重跑一次 `adb install -r` 即 `Success`**。
判据：日志尾部出现 `* daemon not running; starting now at tcp:5037` + `device ... not found`。

### 踩坑：混合编码日志

`build-real.ps1` 用 `*>` 重定向 gradle 输出（**UTF-16LE**），
之后又用 `Out-File -Encoding UTF8` **追加** ASCII 行 → 同一文件两种编码。
整体按 `utf-16` 解码会把追加段变成乱码；**正确读法：尾部按 utf-8 解码**（`open(p,'rb').read()[-900:].decode('utf-8','replace')`）。

### 踩坑：`input swipe` 会误切 Tab

在这台 ROM 上连续/快速 `input swipe` 有时会被解释成切页手势（实测两次把页面从「设置」切到了「合成」/「变声」）。
**对策**：单次慢速滑动（duration ≥ 800ms），且每次滑动后 **dump UI 确认当前 Tab 与可见文本**，
不要盲目连滑后直接截图。
