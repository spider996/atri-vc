## ⚠️ 最重要的一条方法论（必须记住）

**在 NSF 声码器（RVC）上，端到端「波形余弦」是无效判据。**
ONNX vs PyTorch 波形 cos 只有 **0.48**，一度当 bug 排查，最后确认是**假警报**：
- net_g 内含随机激励（SineGen 的 `randn_like`，ONNX 版也有）→ 两次推理本就不同；
- 40k 波形相位对微小扰动极敏感。
用频谱级（对相位不敏感）判等才正确，四组对比：ONNX vs ONNX 0.9686 / PyTorch GPU vs CPU 0.9699 /
ONNX vs PyTorch CPU 0.9641 → **ONNX 与 PyTorch 的差 ≈ 同实现跑两次的天花板**，即等价。

### ⚠️⚠️ 本次最重要的发现：ORT 的 intra-op 线程数会让 INT8 结果「分档」

**同一个 ONNX 文件、同一台机器、同一输入，只改 `intra_op_num_threads`：**

|---|---|
| 默认（32核自动） | **maxAbs 0.000e+00（逐位相同）** |
| 4 / 8 | 2.214e+00, cos 0.99409469 |
| 12 | 2.212e+00, cos 0.99409420 |
| 16 / 20 / 22 / 24 / 32 | **0.000e+00（逐位相同）** |

- **教训**：这个 0.994 我一度判成「Android 平台 INT8 内核差异」，绕了很大一圈。
  正确顺序应该是：**先怀疑自己传的参数，再怀疑平台**。判定手段＝「同一台机器上只改这一个参数」。

### 算子级剖析（ORT profiling，CPU EP，net_g 总 12510 ms / 10188 node）

QLinearConv 49.5%（1368 次，均 4.5ms）· **ConvTranspose 14.5%（36 次，均 50ms）** ·

两个结论：
1. **Transpose + Q/DQ 合计 21% 是"白给"开销**，可通过图优化消除（`onnxruntime.transformers.optimizer`）。
2. **CPU 利用率只有 ~3.5 核**（8 核设备，采样并行度 3.0–3.8×）。

### 检验方法（重要：比 cos 强得多）

导出脚本里的 cos 只证明「**我手写的封装** torch vs ORT 一致」，**证明不了封装本身与官方语义一致**。补了三个脚本：

- `gsv_verify_t2s.py`：直接调官方 `mdl.t2s_transformer.process_prompt / decode_next_token` 取 logits 对照。
  结果 encoder xy_pos cos 1.0、**mask 逐位一致**、prefill/decode logits 相对 L2 ~1e-6、连续 5 步 argmax 全一致。
- `gsv_verify_s2.py`：用官方 `module.models.SynthesizerTrn` 对照 spec/prompt/vits。
  关键技巧：**monkeypatch `torch.randn_like`** 注入固定噪声，让官方 `decode()` 与 ONNX 走同一噪声才能逐位比。
- `gsv_verify_ar_e2e.py`：**决定性检验** —— 给官方 `infer_panel` 和 ONNX 循环设**同一个 torch.manual_seed**，
  逐 token 比较。因 `sample()` 用 torch RNG，同种子必须得到完全相同的 token 序列。

### ⚠️ 四个必须记住的坑

1. **EOS 截断差一步 → AR 直接跑偏**（本次最大的 bug）
   官方 `infer_panel_naive` 循环变量**从 0 开始**、条件 `if idx < 11` ⇒ 共 11 步截掉 EOS 通道(index 1024)。
   我的循环从 1 开始沿用 `< 11` 只截了 10 步 → 从第 12 个 token 起与官方分叉，表现为
   **生成长度在 13~89 token 之间乱跳（半句话）**。改成 `if idx <= 11` 后，
   5 个种子下 token 序列与官方**完全一致（首个不同位置 = -1）**。
   定位手段就是「首个不同位置 = 11/12」这个数字，正好卡在边界上。
2. **官方 `T2STransformer.decode_next_token` 会原地修改 k/v cache（list 内元素被替换）**。
   对照实验里第二次调用会拿到已多一帧的 cache → 与 ONNX 错位一格，
   表现为「单步 cos 1.0 但连续 5 步 cos 掉到 0.9967、argmax 全错」。**每次对照必须传 clone。**
3. **`export_torch_script.sample()` 是 TorchScript 函数，`top_p` 签名是 `Optional[int]`** ——
   传 `1.0` 直接 RuntimeError，必须传 `top_p=1`。
4. **参考音频三条前端路径各不相同（官方就是这么写的，别"统一"它）**：
   - `ssl`：librosa 16k 波形 **尾部接 9600 个零**（`pause_second=0.3 × 32000`，注意是 32k 采样率算出来的长度却接到 16k 波形上）；
   - `refer`：`torchaudio.load` → 重采样到 **32k** → `spectrogram_torch(center=False)`；
   - `sv`：把上一步的 32k **再重采样回 16k**（不加零填充）→ ERes2NetV2。

### 质量旋钮（新发现，App 要用）

同种子下 ONNX 与官方逐 token 一致，所以**生成长度乱跳是官方模型/采样参数的固有行为**：
30 个种子扫描，token 数 13~89、中位 44，其中约 **27% 的种子会在 11 步后立刻 EOS 出半句话**。
把「强制禁用 EOS 的步数」从官方硬编码的 11 提到 **45** 后，20 个种子全部落在 45~84 token（1.8~3.4s）
→ **半句话彻底消失**。已作为 `AR_MIN_STEPS` / `AR_SEED` 两个环境变量接进 pipeline（Task #24）。

## GPT-SoVITS 量化与体积取舍（2026-09-30 深夜，Task #19 完成）

**结果：2612.9 MB → 762.1 MB（3.43x，档 C），音质近无损；端到端总耗时 7.04s → 4.99s。**

### 🔑 核心规律：动态 INT8 必须按「算子构成」分档，不能按模型一刀切

| 模型 | 主干 | Conv 权重占比 | INT8 cos | 判定 |
|---|---|---|---|---|
| bert | MatMul×176 | 0% | 0.991（传导到 AR logits **0.9999952**，argmax 不变）| ✅ 可用 |
| t2s_prefill / decode | MatMul×145 | 0% | **0.99972 / 0.99980** | ✅ |
| ssl (huBERT) | MatMul+Conv | 9% | **0.8223** | ❌ |
| vits (vocoder) | Conv207+Gemm80 | 73% | **0.3403** | ❌ |
| sv (ERes2NetV2) | **全 Conv×159** | **100%** | **0.2491** | ❌ |

→ **Conv 占比越高崩得越狠**（ORT 动态量化对 group/depthwise Conv 的 per-channel 处理误差被放大）。
→ 全量 INT8 虽然能到 694.6 MB（3.76x），但端到端 **rms 从 0.0864 掉到 0.0048（1/18）**、mel 质心 2858→7881 Hz、谱平坦度 0→0.0071（噪声化），**完全不可用**。

### 🔑 替代手段一：fp16 权重存储 + fp32 计算（Conv 网络的最优解）

不要用 ORT 的 `convert_float_to_float16`（整图变 fp16，CPU EP 缺 kernel 到处插 Cast，反而更慢）。
自写 `tools/gsv_fp16.py`：**initializer 存 fp16 + 每个权重前插一个 `Cast→fp32`**，计算图语义不变。

实测精度（对比 fp32）：bert / t2s 全系 **cos 1.0000000（relL2=0，逐位相同）**；prompt token 100% 一致；
ssl 1.0；**vits 0.9999974（rms 完全一致）**；sv 0.9999713。体积 2613→1316 MB（1.99x）。

### 🔑 替代手段二：参考音频特征离线预计算（543 MB → 1.69 MB）

`ssl + sv + prompt + spec` **只依赖参考音频**，与目标文本无关 → 离线跑一次存 4 个中间量即可
（`tools/gsv_precompute_ref.py`，npz 压缩后 **1.69 MB**，且用 fp32 算的比 fp16 模型更准）。
**收益远超任何量化，且完全无损**，还省掉 1.3 s 的 ref 阶段推理。
已验证预计算模式与在线模式端到端结果完全一致（档 C 在线/预计算均 62 步、rms 0.08569）。
代价：参考音频固定；若要支持用户自录，需保留 ssl/sv/prompt/spec（fp16 共 272.0 MB）。

### 🔑 顺带发现：t2s_prefill 与 t2s_decode 是同一份权重

逐 tensor MD5 比对 **192/193 个完全相同**（仅 1 个形状不同），名字差异是 torch 导出的 `onnx::MatMul_XXXX`
自动编号错位。若改 external data 共享或合并为单模型，可再省 **145.5 MB(fp16) / 74.1 MB(int8)**。本次未做。
