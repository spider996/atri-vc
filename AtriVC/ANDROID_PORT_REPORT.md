# 亚托莉变声器 · Android 移植验证报告

**日期**：2026-09-30
**验证方式**：x86_64 Android 模拟器（WHPX 加速）端到端跑通，并与 PC 端管线逐级比对
**结论**：**移植正确，端到端可用。** App 在模拟器上完成了「模型加载 → 导入音频 → 离线变声 → 导出」全流程；
内容特征链（HuBERT）与 PC 基准**逐位相同**，最终合成波形与基准的差异**完全来自 ONNX Runtime 的线程分档**，
不是逻辑缺陷。

## 4. 关键发现：ORT 的 intra-op 线程数会让 INT8 结果「分档」

这是本次最有价值的发现，也是最容易误判为「安卓移植出错」的陷阱。

同一台 PC、同一个 `hubert_dyn8.onnx`、同一份输入，只改 `intra_op_num_threads`：

| `intra_op_num_threads` | maxAbs | cos | 档位 |
|---|---|---|---|
| **默认（32 核自动）** | **0.000e+00** | **1.00000000** | A |
| 4 / 8 | 2.213622e+00 | 0.99409469 | B |
| 12 | 2.211507e+00 | 0.99409420 | C |
| **16 / 20 / 22 / 24 / 32** | **0.000000e+00** | **1.00000000** | A |

- `inter_op_num_threads = 1` **不影响**结果（单独设它仍逐位相同）。
- 线程数相同档位内结果**逐位相同**；跨档位则系统性不同。
- 机制推断：MLAS 的 INT8 QGEMM 会按线程数决定 **K 维是否参与切分**，切分后量化累积的
  分组/取整方式不同 → 浮点结果分档。属于 ONNX Runtime 内部行为，不是我们的 bug。

**推论**：PC 基准是 32 线程跑出来的（A 档）。**任何核心数 < 16 的设备都必然落在 B 档**，
所以手机上不可能靠「调参」复现基准——除非**超订线程**（在 4 核设备上硬设 16 线程，实测有效）。

**代码对策**（已落地）：

- `VcEngine.load(threads = 0)` 表示「跟随 ORT 默认」，默认不再显式设置线程数；
- UI 滑块放开到 `0`，显示为「自动（ORT 默认）」；
- 调试通路可被 `<外部目录>/threads.txt` 覆盖，用于严格对齐验证。

## 5. 为什么最终波形 cos 只有 0.42（不是问题）

| 现象 | 数据 |
|---|---|
| App 输出 vs CLI 输出 波形 cos | 0.9979（最接近的一对） |
| CLI 输出 vs PC 基准 波形 cos | 0.4176 |
| App(16线程) vs PC 基准 波形 cos | 0.4172 |
| 三者之间 log-mel 余弦 | 0.9986 ~ 0.9991 |
| F0 Pearson（App 输出 vs 基准） | 0.999444，平均差 **0.65 Hz**，中位数 380.7 vs 378.5 |

原因：`blocks_phone` 有极少数元素差到 0.33（均值仅 2.3e-05），而 net_g 的 NSF 生成器对
激励的相位是**积分式**的——微小差异会沿时间累积成相位漂移，导致波形去相关，但**频谱与音高完全保持**。
这一点桌面 JVM 管线与 App 表现**完全一致**（0.4176 vs 0.4172），说明是管线固有性质，不是移植引入的。
**波形余弦不适合作为 NSF 类声码器移植的正确性判据**，应看 log-mel 余弦 + F0 相关。

另有一处固有噪声：**net_g 在 Android 上逐次运行结果不完全一致**
（两次同配置运行：`blocks_phone` 及之前全部逐位相同，只有 `blocks_audio` 差 cos 0.99776），
属库内部并行归约顺序问题，量级远小于可听阈。
