## 1. 部署（含一个必踩的坑）

| 步骤 | 结果 |
|---|---|
| `adb install` | ❌ `INSTALL_FAILED_USER_RESTRICTED` |
| 设备端 `pm install` | ❌ 同样被拒 |
| 打开开发者选项「通过 USB 安装」后 | ✅ 成功 |

**坑**：HyperOS（V816 / OS3.0）对侧载有系统级拦截，与包本身无关。`adb install` 和设备端 `pm install` 两条路都会被拦，**只能靠手机侧开关放行**。

模型部署走 **App 外部私有目录**（`/sdcard/Android/data/com.atri.vc/files/models/`）：

- App 首次启动时系统会自建该目录（属主 = App uid），此后 `adb push` 进去的文件 App 可直接读（文件 group 是 `ext_data_rw`，App 在该组内）
- 4 个文件 md5 与宿主机**逐一吻合**（含 287 MB 传输校验）

## 2. 正确性：PASS

### 2.1 逐级对齐（裸 16 kHz 输入 + 复用 PC 基准噪声块）

| 阶段 | maxAbs | cos | 判定 |
|---|---|---|---|
| hubert_feat | 3.486e+00 | **0.99313037** | 见下 |
| feat_after_index / feat_interp | 3.241e+00 | 0.99392611 | 继承 hubert |
| mel（纯 Kotlin DSP）| 2.979e+00 | **0.99998653** | ✅ |
| rmvpe_hidden | 1.488e-01 | **0.99983722** | ✅ |
| f0 / pitchf | 3.127e+02 | **0.99944461** | ✅ |
| protect_weight | 6.700e-01 | **0.99961782** | ✅ |
| feat_final / blocks_phone | 3.241e+00 | 0.99389805 / 0.99400268 | 继承 hubert |

**关于 hubert 的 0.99313**：这不是移植缺陷，而是 **INT8 内核算术差异**，有三条独立证据：

1. **真机是确定性的**：`threads=4` 与 `threads=8`（默认）两次运行的 hubert 输出 **逐位完全相同**（cos 完全相同、maxAbs 完全相同）
2. **量级在 INT8 量化误差之内**：此前实测该模型 INT8 对 fp32 本就有 cos 0.9846–0.9916 的偏差；桌面 x86_64 换线程档位也会产生 0.9941 的差异
3. **后续非 INT8 环节全部 PASS**（mel 0.99999、rmvpe 0.99984、f0 0.99944）

即：**arm64 的 NEON 8-bit dot 内核与 x86_64 的 AVX2/VNNI 累加顺序不同，跨架构不可能逐位一致**，这是量化推理的固有性质。

### 2.2 最终音频（最优配置：CPU EP + 块并行 4）

| 指标 | 真机 arm64 | 同噪声天花板 | 判定 |

### 2.3 并行改造的数值等价性（重要）

块级并行是本次新加的优化，必须证明它不改数值：

| 阶段 | par=4 vs par=1 |
|---|---|
| hubert_feat … **blocks_phone**（全部中间产物）| **maxAbs = 0.000e+00 → 逐位相同** |
| blocks_audio（net_g 输出）| cos 0.99778883 |
| out_40000 | cos 0.99771742 |

`blocks_phone` 及之前**逐位相同**说明输入完全没变；`blocks_audio` 的 0.9978 与**同配置两次串行运行**测到的差异（0.99776）**量级完全相同**，是 ORT 多线程浮点归约顺序的固有噪声。

net_g 总计 **12510 ms**，10188 个 node：

| 算子 | 耗时 | 占比 | 次数 | 平均 |
|---|---|---|---|---|
| QLinearConv | 6121 ms | 49.5% | 1368 | 4.5 ms |
| ConvTranspose | 1786 ms | 14.5% | 36 | **50 ms** |
| **Transpose** | **1467 ms** | **11.9%** | 1179 | 1.2 ms |
| QuantizeLinear | 578 ms | 4.7% | 1458 | — |
| DequantizeLinear | 552 ms | 4.5% | 1737 | — |

| CumSum | 408 ms | 3.3% | 18 | 23 ms |
| QLinearMatMul | 150 ms | 1.2% | 234 | — |

**两个发现**：

1. **`Transpose + Q/DQ 合计 21%** 是"白给"开销**——纯数据重排和格式转换，本可通过图优化消除
2. **CPU 利用率只有 ~3.5 核**（采样 8 核设备推理期间并行度 3.0–3.8×），近一半核心闲置

## 6. 结论与后续

### 离线转换：可用

最优配置下 20 秒音频 15.1 秒处理完（1.32× 实时）。对"导入音频 → 导出变声结果"这个场景完全够用。

### 低延迟实时变声：当前方案做不到

必须如实说明三点：

1. **块长是硬约束**：net_g 是固定 1024 帧（= 10.24 秒音频）的静态图，意味着**单次最小延迟就是 10 秒**。这与实时变声要求的 50–200 ms 差两个数量级
2. **缩小块长不等于线性变快**：块越小，每个 node 的固定开销占比越高，ORT 的并行效率越差
3. **CPU 路径已接近其能力上限**：8 核只用到 3.5 核，且 21% 花在 Transpose/Q-DQ 这类非计算开销上

### 后续优化建议（按性价比排序）

1. **模型图优化**（省 ~21%，风险低）：用 `onnxruntime.transformers.optimizer` 或手写 onnx 图变换，消除冗余 Transpose + 融合残留 Q/DQ
2. **导出可变块长的 net_g**（解决延迟问题的前提）：把 `torch.export` 的动态形状搞定（此前卡在 "T was inferred to be a constant"），这样才能用小块做流水线
3. **降低 overlap 使块数 3→2**（省 ~33%，需评估音质）：当前 `overlapFrames=64`，改 0 后 20 秒音频只需 2 块
4. **换 NPU**：ORT 的 NNAPI EP 在这张图上不可用；若要走 NPU 需换推理框架（如 TFLite/NeuroPilot）或自写算子
5. **ConvTranspose 替换**（省 14.5%）：36 次调用平均 50 ms，是全图单算子最慢的一类

### 环境限制备忘

- **模拟器数字对手机无参考价值**（x86 翻译层 + 4 核）：模拟器 RTF 0.95 vs 真机 0.81，且数值档位也不同
- 真机调试通路：外部目录放 `AUTORUN` 触发全自动流程；`threads.txt` / `ep.txt` / `parallel.txt` / `profile.txt` 可分别覆盖线程数、执行提供器、块并行度、开启算子级剖析
